# Run settings

Issue #69 adds an options editor to the project run flow. Edits stay in the active run draft. They are stored with the run when it starts. Saved operator presets and settings files are described in [settings-files.md](settings-files.md).

The Settings section is a workspace (issue #139). The preset, the engine and **Review and start** sit on top. A rail on the left holds search, **Changed only**, the nine groups with their changed counts, **Compare to defaults** and the saved presets. The groups follow as one long page with sticky headings, and the rail marks the group being read. **Changed only** is kept in the address (`#/projects/:id/settings?changed`), so a reload keeps it. The comparison lists each option that differs from the engine's defaults, or from the preset the run started from, with this run's value and a reset per row. **Review and start** stays disabled while a row holds a value the engine does not accept, and says which rows. Otherwise it opens the Review section (issue #141) at `#/projects/:id/review`. Settings and Review share one draft, so **Back to settings** finds every edit where it was. Review opened from the sidebar before **Review and start** sends the operator to Settings.

The editor uses the selected engine's reconciled option types, domains and defaults. Known options use the reviewed catalogue text. New engine options appear in the unexplained group with the engine's help. Every option the task API reports is a row (ADR 0012). The three formats the task API forces are locked on. Map tiles and GPU use show the server's value as their default: map tiles on, and no GPU on a local engine that has none. The server sends that value only while the row stays at its default, so an edit reaches the engine as the operator set it. The process count has no server value: its default is the engine's own, the core count the task API reports, and a run sends it only when the operator changes it. The options the engine reads as a request even at their default (the process count, GPU use, the two JSON files, the ground control switches, and the split, merge and process-steering options) are sent only when they differ from the engine's default.

The shared value validator is used by both the editor and the server. Invalid numeric text remains visible with a row error and cannot be applied. Dependencies explain why a control is disabled. Missing photo facts remain unknown, including for linked ZIPs before processing. Values already chosen for an inactive dependent remain in the draft because the engine decides when they apply.

Applying settings requests a fresh review from the server. The review revision includes the effective options and the engine schema. Start recomputes the review before creating a task. An invalid value, a hidden setting or a changed revision cannot create a task.

Changing engines first fetches a fresh reconciled schema. Valid edits are retained. Unavailable or invalid edits are removed and listed, along with changes to types, allowed values, defaults and effective values. The browser sends only the edits accepted by the new schema. The hamming warning quotes engine help only when the local engine is known to be using the CPU.

## Source checks

- `shared/option-validation.test.ts`, `shared/run-settings.test.ts` and the existing server validation tests cover shared domain rules, incomplete numeric text, preset baselines, dependencies, unknown facts and engine changes.
- `server/projects/project-runs.test.ts` covers edited review and start, exact settings in the task, revision changes, invalid values, schema changes and local CPU warning conditions. It also checks that map tiles, the process count and GPU use take the server's value only while left at their default, and that an edited value is never overwritten. The options the engine reads as a request go only when changed, and the forced formats stay on.
- `web/src/sections/settings/settings-view.test.ts` covers search across the flag and the five texts, the changed state against the engine defaults, the counts per group, the comparison rows and their resets, the allowed values read from each domain shape and the engine's help with its placeholders filled.
- `web/src/sections/settings/SettingsGroups.test.tsx` and `SettingsGroups.browser.test.ts` cover all 80 rows with what each shows, locked options, the folded Expert group, validation, dependencies, unknown options, labels, sticky headings, the rail by keyboard and tablet width.
- `web/src/sections/settings/SettingsSection.browser.test.ts` drives the Settings section on the production routes: search with its count, **Changed only** across a reload, the comparison with its resets, the question before a preset replaces edits, a locked option, an engine change that drops a value, a blocked **Review and start**, the review reached by keyboard, and the text contrast in both themes.
- `web/src/sections/review/Review.browser.test.ts` drives Review on the production routes by keyboard. It covers the screen before any settings are chosen; what will be processed, the engine, the run name, the outputs, the changed options with plain name, flag and value, the options the server sets and the repeated warnings; a blocked start whose notice sits above the buttons with nothing else changed; **Back to settings** keeping the draft; and the start with the values the engine receives. `web/src/sections/review/ReviewSection.test.tsx` checks the same screen's markup.
- `web/src/run-start/RunSettings.browser.test.ts` covers editor-to-review navigation, preserving valid edits when engines change, dropping an incompatible edit, submitting the retained settings and browser requests staying on the interface server.
- Folder and upload browser fixtures retain separate JavaScript and CSS outputs when they include the editor. Their focused build checks reproduced the fixed filename collision.
- The existing hosted real task API test reviews and starts an uploaded-photo run with an edited orthophoto resolution, then verifies completion and archived orthophoto bytes. It checks that the editor's rows match the live test-mode option list, with the exact exception of the list a test-mode package bundles. It checks that an untouched run asks for map tiles and no GPU. It starts a run with one edited option from each of the nine groups and reads them back from the engine's task with exactly those values.
