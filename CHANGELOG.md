# Changelog

## Unreleased

- Rebuild the run screen, which the sample job uses too. The header gives the run's name, its engine, a state pill and the elapsed time. That time is the engine's own processing time, and before the engine reports one, the time since the run was created. Below the header, the engine's stages are listed in plain words, each waiting, running, done, skipped or failed, with the time AIDM UI saw it start. The current stage carries the engine's progress and what the stage does. A finished run shows its results and viewers first, and the fetch progress while AIDM UI fetches them. These sit in a placeholder band that the shared results component of #132 replaces. A failed run comes first with the stage it failed in, the engine's message and the last 40 lines of its log, the first error line marked. The log stays folded behind its line count, and Copy and Save as file take the whole log from the server. The run view gains the engine's processing time, the stage list and the failure range. The server works them out from the log lines it saves, and keeps the stage times and the last processing time in `stages.json` next to the run's log, so they survive a restart of AIDM UI. Nothing shown is an estimate. Evidence: the stage, elapsed time and failure range tests in `shared/run-stages.test.ts`; the run view, its events, the restart and the kept times in `server/runs/run-progress.test.ts`; the screen's markup in `web/src/run/RunScreen.test.tsx` and `web/src/pages/SampleJobPage.test.tsx`; and the Chromium journey on the production routes in `web/src/run/RunScreen.browser.test.ts`, which follows a run from queued through its stages to its results, then a failed run to its lines, and opens the log from the keyboard. Closes #131.
